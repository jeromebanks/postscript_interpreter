# GS_CHECK_INVENTORY.md — every `ghostscript_accepts_*` driver, and what it actually asserts

Issue #95's third acceptance criterion: inventory every
`ghostscript_accepts_*` test **and document its real assertion before
any extraction**. This is that inventory. It is a precondition for the
extraction work, not the extraction itself — see "Why extraction isn't
in this issue" at the bottom.

Generated by reading each test body in full, not by pattern-matching
the function names.

## The count has drifted

`docs/PS_LIBRARY_COUPLING.md` (issue #92, "Touchpoint 2") records **16**
of these across the suite. As of this commit there are **25**:

```
$ grep -c '^fn ghostscript_accepts' tests/*.rs

tests/graph.rs:1    tests/halftonekit.rs:2 tests/handwrite.rs:1

tests/paintkit.rs:9 tests/printkit.rs:1   tests/stipplekit.rs:1
tests/styles.rs:1   tests/surfacekit.rs:1 tests/type1.rs:1
```

That is a 56% undercount in a document written five months of
development ago, and it is itself the argument for keeping this file
current: the number moves every time a library ships. The doc's *other*
claim about this family holds up exactly — `tests/paintkit.rs` is still
the outlier, now with **9** distinct drivers rather than 7.

Three of the 25 are not single driver invocations at all: `fontlib`
loops 7 Type 3 face files, `styles` loops 4 style packs, and `pagekit`
concatenates 5 template calls into one driver. Counting actual `gs`
invocations rather than `#[test]` functions gives **35**.

## The inventory

"Assertion" is what the test checks beyond the process starting.
Everything marked *exit code* asserts only `status.success()` — `gs`
parsed and ran the program without raising. That is a real check (it is
how every cross-interpreter incompatibility in this repo's history was
caught) but it is not a check on *output*.

## What the inventory changes about the extraction plan

`docs/PS_LIBRARY_COUPLING.md` already corrected two wrong first
impressions about this family (not one-per-file; not uniformly
exit-code-only). Reading all 25 in full adds three more things an
extraction has to handle, none of which a uniform
`gs_check.sh <lib> <driver>` covers on its own:

1. **Two shapes of "not exit code only", not one.** The doc names
   `ghostscript_accepts_artkit`'s `GSTILES` band. It has *three*
   parsed assertions, with three different comparison kinds (a range,
   an exact equality, another range) — and `tests/type1.rs`'s
   `ghostscript_accepts_the_same_bytes` is a fourth, an approximate
   float comparison, in a completely different invocation shape (`gs
   -c <script>`, no concatenated library file at all). A script
   interface that only knows "library + driver, assert exit 0" cannot
   express either.
2. **Three drivers are loops, not single invocations.** `fontlib` (7),
   `styles` (4), `pagekit` (5 templates in one driver). Extracting
   these as one script call each silently drops per-item isolation:
   today a single bad face fails with *that face's* path in the
   message.
3. **Ten of the 25 run a committed `examples/*.ps` file directly**
   rather than a concatenated snippet. Those are the cheapest to
   extract (the "driver" is just a path) and should probably be a
   different, simpler script than the concatenate-lib-plus-snippet
   ones.

## The packed-array checks are load-bearing and must not be extracted away

Six drivers (#7, #12, #13, #14, #17, #19) deliberately open with
`true setpacking`. `pscat` does not implement packing at all —
`tests/paintkit.rs`'s own
`setpacking_true_does_not_break_pressure_validation` confirms directly
that `true setpacking { } type` stays `arraytype` under this
interpreter, never `packedarraytype`. Under real `gs` it does change,
which is why row 14 of the doc's defect table ("packed-array
`/Pressure` wrongly rejected") is reachable **only** through these
checks.

No `%%SelfTest` block, however written, can regression-test that class
— the type it is about cannot be produced by the interpreter running
the block. Issue #95 says this explicitly and so does this file:
**Phase A does not replace these, and neither should the extraction.**

## Why extraction isn't in this issue

Issue #95's acceptance criterion for this family is inventory and
documentation "before any extraction", and its Scope section makes
Phase A the deliverable. The three findings above are the concrete
argument for keeping them separate: an extraction that treats the
family as uniform would silently weaken checks 1, 4, 23 and 25, which
is a worse outcome than not extracting yet.

Tracked as **issue #135**, referenced from `docs/SELFTEST.md`'s "What
Phase A does not cover". That issue treats this file as its spec: if
the count or an assertion changes before it lands, update this file
rather than the issue body.
